## 2. 확정된 차이 — API를 바꿔야 하는 것

CSS로 해결되지 않고 서버 스키마·엔드포인트 결정이 필요한 항목이다.

### API-1. 로드맵 단계 카탈로그: 고정 5단계 vs 조건부 7단계

- Figma: `3 / 7단계 진행 중`(C1), `안심상속 원스톱 조회 신청 · 2 / 7단계`(D3), `채무 확인 · 3 / 7단계`(D2), `상속 방식 판단`(J2). 사망신고·안심상속 조회 신청이 앞 단계로 존재한다.
- 코드: `RoadmapService.generate()`가 모든 사건에 동일한 5단계를 무조건 생성한다. `VERIFY_INFORMATION`, `DECISION_SUPPORT`, `HEIR_COORDINATION`, `FINANCIAL_PROCEDURES`, `TAX_REVIEW`.
- 명세: ONB-06은 "필요한 단계만 선별", B5 주석은 "조회 전·조회 중 → 안심상속 신청 단계가 로드맵에 추가됨"이라고 못박는다. 즉 조건부 선별은 Figma만의 요구가 아니라 명세 요구다.
- **차이 확정: 코드가 명세·Figma 양쪽과 다르다. 서버 변경 대상.**
- 결정 필요: (a) 단계 카탈로그를 조건부로 늘릴지, (b) 늘린다면 `inquiryStatus`, `willExists`, `minorHeirExists`, 채무 유무별로 어떤 stepKey를 붙일지. 7이라는 숫자 자체는 Figma의 예시값이므로 고정하지 않는다.

### API-2. 처리 결과 입력 유형: 화면이 결과 유형을 알 수 없다

- Figma: D2 확인형은 `있음 / 없음 / 확인 중`, D3 신청형은 `신청 전 / 신청 완료 / 처리 완료`. 단계마다 시트 종류가 다르다.
- 코드: `Task.tsx:36`이 `step.stepKey === 'FINANCIAL_PROCEDURES'`로 신청형을 판정하고, 선택지 4개를 프런트에 하드코딩한다. `GET /api/tasks/{id}` 응답에 결과 유형이 없다.
- 백엔드 `TaskProgressStatus`에는 `NOT_APPLICABLE, CHECKING, BEFORE_APPLICATION, IN_PROGRESS, COMPLETED` 5개가 다 있으나, 어떤 단계에 어떤 값이 허용되는지 서버가 알려주지 않는다. 현재 프런트는 확인형에도 `NOT_APPLICABLE`을 보여주고, 신청형에도 `NOT_APPLICABLE`을 보여준다.
- **차이 확정: 결과 유형은 단계의 성격이므로 서버가 내려야 한다. 서버 변경 대상.**
- 권고: `RoadmapStep`에 `resultType`(EXISTENCE / APPLICATION)을 두고 `step` 응답에 `resultType`과 허용 상태 목록을 함께 내린다. 허용 목록은 **순서가 보장되는 List**여야 한다(선택지 순서가 UI 순서다).

### API-3. 확인형 결과에 금액이 있다

- Figma D2: `확인된 금액` 입력 + `정확한 금액은 아직 모르겠어요` 체크가 결과 시트 안에 있고, 하단에 `완료 조건: "있음(금액 확정)" 또는 "없음"을 선택해야 단계가 완료`라고 적혀 있다. D5는 완료 카드에 `결과: 있음 / 12,400,000원`을 표시한다.
- 코드: `PATCH /api/tasks/{id}/result`는 `progressStatus, resultDate, resultText, memo`만 받는다. 금액은 `financial-items` 쪽에만 있다.
- **차이 확정: 결과 저장과 금액 확정이 분리되어 있다. 결정 필요.**
- 선택지: (a) 결과 시트에서 관련 `financialItemId`의 금액을 함께 확정하도록 결과 API에 금액 필드를 추가, (b) 결과 시트는 상태만 저장하고 금액은 기존 재산·채무 화면으로 유도. (b)는 Figma의 "단계 완료 = 금액 확정" 규칙을 만족시키지 못한다.

### API-4. 완료 취소(TASK-03)가 없다

- Figma D5: `완료 취소` 버튼, 되돌아가는 범위(현재 단계 이동, 이후 단계 상태 초기화, 입력 금액은 유지)를 사전 고지한다. 명세 TASK-03도 같다.
- 코드: 완료 취소 전용 동작이 없다. `PATCH result`로 다른 상태를 저장해 간접적으로만 되돌릴 수 있고, 되돌아가는 범위를 미리 계산해 보여주는 API가 없다.
- **차이 확정: 서버 변경 대상.** 취소 시 영향 범위를 미리 조회하는 응답(현재 단계 변화, 상태가 바뀌는 단계 목록)이 필요하다.

### API-5. 주의사항에 관련 단계·기한·해소 조건이 없다

- Figma E1: 카드마다 `현재 단계: 채무 확인`, `D-42`, `정보 입력 필요`, `자료 등록 필요` 배지가 붙는다. 목록은 `지금 확인 / 현재 단계 / 이후 단계` 그룹 헤더로 나뉘고, `정렬 변경`과 하단 `해결됨 2` 그룹이 있다. E2는 해소 조건 체크리스트를 보여준다.
- 코드: `GET /api/cases/{caseId}/warnings`는 `resolved=false`만 반환하고, 응답에 관련 단계 제목도 `deadline`도 없다. `Warning` 엔티티에는 `deadline`과 `step`이 있으나 뷰에 담기지 않는다. 화면은 그룹 없이 평면 목록 + 카테고리 칩이다.
- **차이 확정: 서버 응답 필드 부족. 서버 변경 대상.**
- 필요한 것: 응답에 `stepTitle`, `deadline`/`dDay` 추가, `resolved=true` 조회 경로(해결됨 그룹), 정렬 파라미터. 해소 조건 체크리스트는 데이터 모델이 없으므로 신규 설계 대상 — 범위 결정 필요.
- 참고: `resolved`는 `rebuildWarnings()`가 매번 삭제 후 재생성하므로 사용자가 직접 해제하는 개념이 아니다. Figma도 "수동 읽음 처리 없음"이라고 적었으므로 이 부분은 일치한다. 해결됨 목록을 보여주려면 삭제 대신 해결 상태로 남기는 정책 변경이 필요하다.

### API-6. 문서 업로드: 단건 동기 처리 vs 다건 비동기 상태

- Figma H2: `최대 20MB`, 파일 여러 건, 파일별 `분석 중 45% · 금액·기준일 추출 중` / `분석 실패` / `확인 대기 6건` 상태, "분석은 백그라운드에서 진행됩니다".
- 코드: `spring.servlet.multipart.max-file-size=10MB`, 프런트도 10MB로 검사. `Upload`는 파일 1개만 받고, `POST documents/{id}/analyze`를 호출해 동기적으로 끝난 뒤 목록으로 이동한다. 진행률 개념이 없다.
- **차이 확정: 두 가지를 나눠 결정한다.**
  - 용량 20MB: 서버 설정 한 줄 변경이면 되지만, OCR·마스킹·AI 호출 비용과 타임아웃에 직접 영향을 준다. **정책 결정 필요.**
  - 진행률·백그라운드: 분석 작업 상태 API(작업 ID, 상태, 퍼센트)와 폴링이 필요하다. **신규 API 설계 대상.** 퍼센트를 실제로 못 내리면 Figma의 진행률 바는 구현하지 않는 편이 낫다(가짜 진행률 금지).

### API-7. 회원가입 부가 기능

- Figma A2: `중복확인` 버튼, `전체 동의` + 필수 2종(이용약관, 개인정보) + 선택 1종(마케팅). 필수 미동의 시 가입 버튼 비활성.
- 코드: `POST /api/auth/signup`은 `username`, `password`만 받는다. 중복확인 엔드포인트도 동의 저장 필드도 없다.
- **차이 확정: 서버 변경 대상이지만 약관 문구·보존 정책이 먼저 정해져야 한다.** 동작하지 않는 버튼을 화면에만 두지 않는다(HANDOFF의 기존 결정 유지).

### API-8. 문서 확정 시 항목별 선택 반영

- Figma H3: 항목마다 체크박스, `전체 선택`, 제외한 항목은 저장하지 않는다.
- 코드: `PATCH /api/documents/{id}/confirm`이 편집된 `analysis` 전체를 받아 전건 확정한다. 프런트는 "이 항목 제외"로 배열에서 빼는 방식이라 결과는 같지만, 화면 모델(체크 선택)이 다르다.
- **차이 확정: API는 그대로 두고 화면만 바꿔도 된다. 디자인 변경 대상으로 분류.**

## 5. 다음 결정이 필요한 질문

1. 단계 카탈로그를 조건부로 확장할 것인가. 확장한다면 stepKey 목록과 각 단계의 선별 조건·완료 조건은 무엇인가. (API-1)
2. "단계 완료 = 금액 확정"을 서버 규칙으로 넣을 것인가, 화면 유도로 남길 것인가. (API-3)
3. 완료 취소를 이번 범위에 넣을 것인가. (API-4)
4. 업로드 한도를 20MB로 올릴 것인가. AI 호출 비용·타임아웃 검토가 선행되어야 한다. (API-6)
5. 주의사항 해소 조건 체크리스트를 데이터로 관리할 것인가, 화면 문구로 둘 것인가. (API-5)
6. 약관 동의 보존 정책이 정해졌는가. 정해지기 전에는 가입 화면에 동의 UI를 넣지 않는다. (API-7)

1~3번이 결정되면 `RoadmapStep`·`TaskResult` 스키마가 확정되고, 나머지 화면 작업은 API 변경 없이 진행할 수 있다.
